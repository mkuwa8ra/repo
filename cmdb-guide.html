    1-1. CMDBの定義・目的・役割

    CMDB（Configuration Management Database：構成管理データベース）は、ITサービスを提供するために管理が必要な構成要素（CI）の情報と、CI同士の関係を、ライフサイクル全体（導入〜廃棄）を通して記録・維持するためのデータベースです。

    ITILでは、構成管理の目的を「サービスと、それを支えるCIの構成について、正確で信頼できる情報を、必要なときに必要な場所で利用できるようにすること」と説明しています（原文の要約です。正確な定義文は公式出版物で確認してください）。CMDBはこの目的を実現するための情報基盤です。

    目的

    障害対応・変更・脆弱性対応・契約管理などの判断を、正確な構成情報に基づいて素早く行えるようにする。

    役割

    「何が・どこに・どんな状態で・何とつながり・誰が責任者で・どのサービスに使われているか」に答える唯一の参照先（Single Source of Truth）になる。

    位置付け

    CMDBそのものは目的ではない。インシデント管理・変更管理・問題管理などのプロセスから使われて初めて価値が出る。

    1-2. CI（Configuration Item：構成アイテム）とは

    CIとは、ITサービスを提供するために管理（コントロール）する必要がある構成要素のことです。ハードウェアだけではなく、ソフトウェア、回線、クラウド上のリソース、サービスそのもの、場合によっては契約や文書もCIとして扱います。

    種類ネットワーク保守での例
    物理機器ルータ RT-S0123-01、スイッチ SW-S0123-01、無線AP、ファイアウォール
    論理構成VLAN 10（業務LAN）、サブネット 10.20.123.0/24、VPN、冗長化グループ（HSRP/VRRPなど）
    回線閉域網回線 CIR-0123-01、LTEバックアップ回線 CIR-0123-02
    ソフトウェアルータのOS/ファームウェアのバージョン（属性として扱うか独立CIにするかは設計次第：3章参照）
    サービス拠点WAN接続サービス、無線LANサービス、インターネット接続サービス
    場所拠点（横浜港北店）、データセンター、ラック
    ポイントCIは「管理すべきもの」であって「存在するものすべて」ではありません。LANケーブル1本ごとや、刻々と変わるARPテーブルのエントリをCIにすると、管理コストが価値を上回ります（3章で判断基準を扱います）。

    1-3. なぜ機器台帳だけでは不十分なのか

    多くの組織には、Excelの「機器台帳」がすでにあります。台帳はCMDBの出発点として有用ですが、台帳は「モノの一覧」にとどまりがちです。

    観点一般的な機器台帳CMDB
    管理単位機器（1行＝1台）CI（機器・回線・サービス・論理構成など）
    関係性ほぼ無い（「備考」欄に書く程度）「接続」「設置場所」「依存」「保守契約」などを構造化して保持
    サービスとの紐付け無いCIがどのサービスを支えているかが分かる
    状態・ライフサイクル「稼働/撤去」程度、更新されにくい計画〜廃棄までのステータスを定義し、変更と連動して更新
    履歴上書きされて消える変更・交換・障害の記録と紐付く
    情報の信頼性いつ誰が何を根拠に書いたか不明更新日・更新者・情報源・最終確認日を保持
    プロセス連携無い（人が都度参照）インシデント・変更チケットからCIを参照する

    具体例：台帳で分かること・分からないこと

    台帳では「RT-S0123-01／機種RX-1000（架空）／横浜港北店／シリアルFTX1234」までは分かります。しかし、障害が起きたときに本当に必要な次の問いには答えられません。

    • このルータが止まるとどのサービスが止まるのか？（POS決済？ 無線LAN？）
    • どの回線につながっていて、回線の問い合わせ先と回線IDは何か？
    • どの保守契約でカバーされ、オンサイト保守は何時間以内に来るか？
    • 先週の変更作業で何か設定を変えていないか？
    • バックアップ回線があるので縮退運転で済むのか、完全停止なのか？

    業務導入前導入後（期待される姿）

    1-5. CMDBがない組織で起きがちな問題

    • 「この機器、誰のもの？」問題：撤去してよいか判断できず、使われていない機器に保守費を払い続ける。
    • 影響範囲の見落とし：スイッチの再起動で、別部門の監視カメラ用VLANまで止めてしまう。
    • 情報の分散：IPはIPAM、回線は契約書PDF、機器はExcel、設定はファイルサーバ…で、障害時に5か所を見に行く。
    • 台帳の陳腐化：機器交換後にシリアル番号が更新されず、保守ベンダーへの申告が誤る。
    • 属人化：「あの拠点はAさんしか分からない」。異動・退職で知識が失われる。
    限界・デメリットも理解する CMDBは導入するだけでは何も解決しません。維持するための人手と仕組みが継続的に必要です。不正確なCMDBは「信じて間違った判断をする」原因となり、無いより悪い場合さえあります。目的と範囲を絞り、更新が回る仕組みとセットで導入することが前提です（10章参照）。

    3. CI（構成アイテム）の考え方

    この章のゴール：「何をCIにするか」「どの粒度で管理するか」を、自分の組織の目的から判断できるようになる。

    3-1. 何をCIとして管理するのか（判断基準）

    次の問いに1つ以上「はい」なら、CI候補です。2つ以上なら優先的にCI化を検討します。

    1. サービス影響：それが止まる・変わると、サービスに影響するか？
    2. 変更統制：それを変更するとき、承認や記録が必要か？
    3. 障害対応：障害時に、それを特定・交換・問い合わせする必要があるか？
    4. 契約・費用：保守契約、ライセンス、回線契約など、契約や費用の対象か？
    5. 監査・セキュリティ：監査や脆弱性対応で、対象として列挙を求められるか？

    逆に、次のものはCIにしない（または属性・他システム参照にとどめる）のが一般的です。

    • 消耗品・低価値品：パッチケーブル1本、マウス（ただし幹線の光ケーブルは管理する組織もある）
    • 高頻度で変わる動的情報：MACアドレステーブル、ARP、セッション、トラフィック量 → 監視・ログ系ツールで扱う
    • 他のシステムが「正」の情報：IPアドレス1個ずつの割当（IPAMが正）、ユーザーアカウント（ディレクトリが正） → CMDBは参照・連携
    • 誰も使わない情報：目的に紐付かない項目は、収集・更新コストだけがかかる

    3-3. CIの粒度をどう決めるか

    粒度とは「どの単位を1件のCIとして扱うか」です。粗すぎると影響範囲や交換対象を特定できず、細かすぎると更新が回らなくなります。

    粗すぎる例

    「横浜港北店ネットワーク一式」を1CIにする → 障害時にどの機器か分からず、シリアル番号も持てない。

    適切な例

    ルータ1台、スイッチ1台（スタックは論理1台＋メンバ）、回線1本、VLAN 1つを各1CIにする。

    細かすぎる例

    スイッチの全ポート（48ポート×数千台）を個別CI化 → 更新不能。ポート情報は自動収集の結果として参照する。

    粒度を決める5つの問い

    1. その単位で交換・発注するか？（交換単位）
    2. その単位で変更作業を行うか？（変更単位）
    3. その単位で障害を切り分けるか？（障害単位）
    4. その単位で責任者や契約が異なるか？（責任単位）
    5. その単位の情報を継続して更新できるか？（維持可能性）← 最も重要

    判断が分かれやすいケース

    対象選択肢推奨の考え方
    スタック構成スイッチA: 論理1台のみ／B: 物理メンバのみ／C: 論理1台＋物理メンバ運用は論理単位（1つのホスト名・管理IP）で、交換・保守はシリアル単位なので C が実務的。メンバは「member_of」関係で論理CIに紐付ける
    冗長構成FW（2台）クラスタ1件／物理2台物理2台＋クラスタ（論理CI）。片系障害を「縮退」として表現できる
    OS・ファームウェア機器の属性／独立したソフトウェアCIまずは属性（バージョン文字列）。脆弱性管理を高度化する段階で、ソフトウェア製品マスタと紐付ける
    無線AP（各拠点数台〜数十台）1台ずつ／拠点ごとにまとめる交換・保守はシリアル単位なので1台ずつ。ただし手動管理はつらいので、WLCやクラウド管理ツールからの自動連携を前提にする

    3-4. CIの属性（Attribute）とは

    属性は、CIの特徴を表すデータ項目です（ホスト名、機種、シリアル番号、ステータスなど）。属性は次のグループで考えると漏れと過剰を防げます。

    グループ例使われる場面
    識別CI ID、ホスト名、シリアル番号、資産番号重複防止、ベンダー問合せ
    分類CIクラス、メーカー、機種、役割（コア/エッジ）脆弱性対象抽出、標準構成確認
    状態ステータス、重要度、環境（本番/検証）影響判断、棚卸し
    構成OSバージョン、管理IP、設置ラック更新計画、リモート接続
    責任オーナー、管理担当、利用部門エスカレーション、引継ぎ
    契約・期限保守契約、保守期限、EOS/EOL日契約更新、リプレース計画
    管理メタ情報更新日時、更新者、情報源、最終確認日データの信頼性判断

    3-5. CI同士の関係性（Relationship）とは

    関係は、CI同士がどうつながっているかを表すデータです。CMDBが台帳と決定的に違うのはここです。関係には向きと種類があります。

    関係タイプ（例）意味例（A → B）影響の伝わり方
    located_in（設置場所）AはBに設置されているRT-S0123-01 → 拠点S0123拠点の停電・閉鎖 → 機器に影響
    connected_to（接続）AとBが物理/論理的に接続RT-S0123-01 ↔ SW-S0123-01双方向に影響しうる（設計時に向きを決める）
    depends_on（依存）AはBが無いと機能しない拠点WAN接続サービス → RT-S0123-01Bの障害 → Aに影響
    runs_on（稼働）AはB上で動作するRADIUSソフト → 認証サーバBの障害 → Aに影響
    member_of（構成員）AはBの構成メンバスタックメンバ1 → 論理SW、FW-01 → FWクラスタ冗長性がある場合は「縮退」
    uses（利用）AはBを利用するPOS決済サービス → 拠点WAN接続サービスBの障害 → Aに影響
    covered_by（契約対象）AはB契約で保守されるRT-S0123-01 → 保守契約MC-2024-017影響ではなく「連絡先・手配先」を導く
    設計時の注意点関係タイプは最初は5〜8種類程度に絞ってください。種類を増やしすぎると、登録者ごとに使い方がぶれます。また「向き」を必ず定義し、「A depends_on B」と「B depends_on A」が混在しないようにします。

    4. CMDBのデータ構造と設計

    この章のゴール：CMDBを「テーブル」と「JSON」で表現でき、識別子・ステータス・信頼性・重複対策まで設計できるようになる。

    4-1. 全体データモデル

    汎用的なCMDBは、共通属性を持つCIテーブル＋クラス別の拡張属性＋関係テーブルの組み合わせで作るのが基本形です。

    ci_class（CI分類）
    • class_id PK
    • class_name
    • parent_class_id FK
    • description
    ci（CI共通属性）
    • ci_id PK
    • class_id FK
    • name
    • status
    • criticality
    • location_ci_id FK
    • owner_group / support_group
    • source / verified_at
    • updated_at / updated_by
    ci_network_device（拡張）
    • ci_id PK/FK
    • hostname
    • vendor / model
    • serial_no
    • os_version
    • mgmt_ip
    • eos_date / eol_date
    ci_relationship（関係）
    • rel_id PK
    • source_ci_id FK
    • rel_type FK
    • target_ci_id FK
    • redundancy_group
    • source / verified_at
    rel_type（関係タイプ）
    • rel_type PK
    • forward_label（依存する）
    • reverse_label（依存される）
    • propagates_impact
    contract（契約）
    • contract_id PK
    • vendor_id FK
    • type（保守/回線）
    • sla / start / end
    ci_history（変更履歴）
    • hist_id PK
    • ci_id FK
    • field / old / new
    • change_ref（RFC番号）
    • changed_at / by
    ticket_link（チケット連携）
    • ci_id FK
    • ticket_type（INC/CHG/PRB）
    • ticket_id

├─ クラウドリソース（Cloud）   … VPC/VNet / VPN Gateway
└─ サービス（Service）
    ├─ 技術サービス（Network Service）… 拠点WAN接続 / 無線LAN / インターネット接続
    └─ 業務サービス（Business Service）… POS決済 / 社内ポータル

    上位クラスで共通属性（名前・ステータス・オーナー等）を定義し、下位クラスで固有属性（回線IDや帯域など）を追加する「継承」の考え方です。

    4-3. テーブル定義の例（SQL）

    -- CI共通テーブル
CREATE TABLE ci (
  ci_id          VARCHAR(20) PRIMARY KEY,   -- 例: CI-000123（不変の内部ID）
  class_id       VARCHAR(30) NOT NULL,      -- 例: router
  name           VARCHAR(100) NOT NULL,     -- 表示名（通常はホスト名）
  status         VARCHAR(20) NOT NULL,      -- planned / in_stock / building / active / maintenance / retiring / retired / disposed

  location_ci_id VARCHAR(20),               -- 設置拠点のCI ID

  user_dept      VARCHAR(50),               -- 利用部門
  source         VARCHAR(20),               -- manual / discovery / contract / import
  verified_at    DATE,                      -- 実機・現地で最後に確認した日

  updated_by     VARCHAR(50),

);

-- ネットワーク機器の拡張属性
CREATE TABLE ci_network_device (
  ci_id       VARCHAR(20) PRIMARY KEY REFERENCES ci(ci_id),

  vendor      VARCHAR(50),

    4-5. 識別子の扱い：何を「主キー」にするか

    識別子特徴主キーにしてよいか扱い方
    CI ID（内部ID）CMDBが採番。意味を持たない○ 推奨一度振ったら変えない。他システム連携のキー
    資産番号（管理番号）資産ラベル。資産管理が採番△物理機器の識別補助。論理CI（VLAN等）には存在しない
    シリアル番号メーカーが付与。物理的に一意△（物理機器のみ）重複判定（突合）の最有力キー。交換（RMA）で変わる点に注意
    ホスト名命名規則で付与。人が読みやすい✕拠点移転・役割変更で変わる。表示名・検索キーとして使う
    IPアドレス設定で変わる。複数持つ✕属性（管理IP）として保持。IP全体の管理はIPAMを正とする
    機器交換時の識別問題（重要）故障でルータを同型機に交換すると、ホスト名・IP・設定は同じでもシリアル番号が変わります。「論理的な役割（ルータRT-S0123-01というポジション）」と「物理的な個体（シリアルFTX...）」のどちらをCIとするかは、組織で決めておく必要があります。
    • 方式A（個体＝CI）：新しい個体を新CIとして登録し、旧CIは「撤去」。資産管理と整合しやすいが、関係を付け替える手間がある。
    • 方式B（役割＝CI）：CIはそのまま、シリアル属性を更新し、交換履歴に旧シリアルを残す。運用は楽だが、個体の追跡は履歴頼み。
    ネットワーク保守の現場では方式Bが選ばれることも多いですが、どちらが正解というものではありません。交換履歴を必ず残すことが両方式に共通する条件です。

    4-9. 重複登録・データ不整合への対処

    識別ルール（Identification Rule）を決める

    新しいデータが来たとき「既存CIと同じものか」を判定するルールです。

    ネットワーク機器の識別ルール（優先順）
 1. serial_no が一致 → 同一CI
 2. asset_tag が一致 → 同一CI
 3. hostname 一致 かつ location 一致 → 同一CI候補（人が確認）
 4. いずれも不一致 → 新規CI候補（自動登録せず「未確認」キューへ）

    不整合チェックの例（定期実行）

    -- ① シリアル番号の重複
SELECT serial_no, COUNT(*) FROM ci_network_device
GROUP BY serial_no HAVING COUNT(*) > 1;

-- ② 稼働中なのに設置拠点が無いCI
SELECT ci_id, name FROM ci
WHERE status = 'active' AND location_ci_id IS NULL;

-- ③ 撤去済なのに、稼働中サービスから依存されているCI
SELECT r.source_ci_id, r.target_ci_id
FROM ci_relationship r JOIN ci t ON r.target_ci_id = t.ci_id
JOIN ci s ON r.source_ci_id = s.ci_id
WHERE r.rel_type = 'depends_on' AND t.status = 'retired' AND s.status = 'active';

-- ④ 1年以上、事実確認されていない稼働中CI
SELECT ci_id, name, verified_at FROM ci
WHERE status = 'active' AND verified_at < CURRENT_DATE - INTERVAL '365 days';
    実務のコツ重複を見つけたら「どちらかを削除」ではなく、統合（マージ）します。残すCI IDを決め、関係・履歴・チケットリンクを付け替えてから、もう一方を「merged（統合済）」ステータスにして参照先を記録します。いきなり削除すると、過去チケットからの参照が切れてしまいます。

    具体例：B社に「横浜港北店のスイッチが壊れた」ではなく「契約MC-2024-017、機種LS-2200P、シリアルJAE1111A2BC、設置場所はバックヤード、店舗は10時開店で裏口から入館」と伝えられるため、手配のやり取りが減ります。
    注意点：交換後のシリアル更新漏れが最も多い不整合です。交換チケットのクローズ条件に「CMDB更新済」を入れます。

    RFC起票対象CIを選択
    →
    影響抽出依存しているサービス・利用部門・重要度
    →
    時間帯判断サービス提供時間（店舗10-21時）を避ける
    →
    周知利用部門へ事前連絡
    →
    承認CABなどで判断

    具体例：SW-S0123-01の再起動では、VLAN30（監視カメラ）も止まることがCMDBから分かり、警備担当への連絡が漏れずに済む。

    6-4. 脆弱性対応時の対象機器抽出

    ベンダーから「機種LS-3400、OS 16.12.0〜16.12.9に深刻度の高い脆弱性」と公表された場合：

    SELECT c.name, d.model, d.os_version, s.name AS site, c.criticality
FROM ci c
JOIN ci_network_device d ON c.ci_id = d.ci_id
JOIN ci s ON c.location_ci_id = s.ci_id
WHERE d.model = 'LS-3400'
  AND d.os_version LIKE '16.12.%'     -- 実務ではバージョン比較関数で範囲判定
  AND c.status IN ('active','maintenance','in_stock')   -- 予備機も対象！
ORDER BY c.criticality, s.name;

    注意点：OSバージョンは手動管理だとすぐ古くなります。自動収集で上書きする対象の筆頭です。また、予備機（in_stock）を対象から外すと、交換時に脆弱なOSの機器が投入されます。

    6-5. OS・ファームウェア更新計画

    現状把握機種×OSバージョンの分布を集計
    →
    標準決定推奨バージョンを決める
    →
    グルーピング拠点タイプ・地域・営業時間で分割
    →
    段階実施パイロット10拠点→100拠点ずつ
    →
    進捗管理CMDBで標準準拠率を可視化

    具体例：「ルータ720台中、推奨バージョン17.6.4は412台（57%）」とCMDBで集計し、残り308台を月80台ペースで更新する計画を立てる。

    6-6. 保守期限・EOS/EOL管理

    EOS（End of Sale：販売終了）、EOL（End of Life：サポート終了）の定義や名称はメーカーによって異なるため（End of Support、End of Software Maintenanceなど）、CMDBには「メーカーの何という日付か」を定義して持たせます。

    抽出条件アクション
    保守契約の期限まで180日以内契約更新の稟議開始
    EOLまで2年以内リプレース計画・予算化
    稼働中なのに保守契約が紐付いていない契約漏れの確認（重大リスク）
    撤去済なのに保守契約の対象のまま契約から除外し、保守費を削減

    6-7. 拠点追加・廃止

    拠点追加（例：S0702 仙台泉店）

    1. 拠点CIを planned で登録
    2. 標準構成テンプレート（タイプB）から機器・回線・VLAN CIを planned で一括生成
    3. 回線開通・機器設置のたびに属性（シリアル、回線ID）を更新
    4. 開店時に一斉に active へ

    拠点廃止

    1. 拠点に located_in する全CIを抽出
    2. 回線解約・保守契約除外・IP返却の漏れを確認
    3. 機器は retired（他拠点へ転用なら in_stock）
    4. サービスとの関係を解除。拠点CIは retired で保持

    注意点：拠点廃止時の回線解約漏れは、毎月費用が発生し続ける典型的な損失です。

    6-8. 監査・棚卸し

    CMDBの「稼働中CI一覧」と、ディスカバリ結果・監視対象一覧・保守契約の対象リスト・現地確認を突合し、差分を是正します。監査ではCMDBそのものの正確性（サンプリングで実機と照合）と、変更管理との連動（変更記録とCMDB更新の一致）が確認されることが多いです。

    6-9. 担当者変更・引継ぎ

    担当する地域を引き継ぐとき、CMDBから「担当拠点の一覧、標準構成からの逸脱、未完了の変更、期限が近い契約、直近半年の障害」を抽出して引継ぎ資料にします。CMDBに載っていない暗黙知（特殊な入館ルールなど）は、この機会にCIの属性かナレッジに移します。

    6-10. 標準構成の確認

    チェック例（タイプB拠点の標準：ルータ1、L3SW1、L2SW≥1、AP≥2、主回線1、LTE1）
  ・LTE回線が登録されていない タイプB拠点 → 12拠点（契約漏れ？未登録？）
  ・OSが標準外のルータ → 37台
  ・ホスト名が命名規則（RT-Sxxxx-nn）に従わないCI → 5件

    逸脱が「本当に逸脱なのか」「CMDBの登録漏れなのか」を切り分けることで、構成の標準化とデータ品質の改善が同時に進みます。

    7-1. スモールスタートの提案

    最初の3か月でやること（ネットワーク保守チームの例）
    • 対象：拠点、WAN回線、ルータ、スイッチ、FW、保守契約 の6クラスだけ（APは数が多いので後回し、または台数のみ）
    • 属性：1クラスあたり必須10項目前後
    • 関係：located_in（設置場所）、connected_to（回線接続）、covered_by（保守契約）の3種類だけ
    • ツール：既存Excel台帳を統合したスプレッドシート（9章）
    • ルール：「機器交換と回線変更のチケットは、CMDB更新を確認してからクローズ」の1つだけを徹底
    • 効果測定：障害時の「回線ID・保守窓口の特定時間」を導入前後で比較

    完璧なデータモデルを作り込むより、小さく作り、使われ、更新される状態を先に作る方が成功しやすいです。使われることで「この項目も欲しい」という本当の要件が出てきます。

    スモールスタートのリスク範囲を絞りすぎると「使えない」と評価され、利用されなくなることがあります。最初の目的（例：障害時の連絡先特定）には確実に答えられる範囲を選んでください。また、将来の拡張を考えて CI IDの採番ルールと命名規則だけは最初に固めておくと、後の移行が楽になります。

    8-4. 正確性の担保と更新漏れの検知

    正確性を担保する仕組み

    • 入力規則（プルダウン、命名規則チェック、必須項目）
    • 属性ごとの「正とする情報源」を一つに決める
    • 自動収集値で手動値を上書きする／差分をアラートする
    • 月次のサンプリング監査（例：ランダム20CIを実機と照合）
    • 品質KPI：正確性（照合一致率）、完全性（必須項目充足率）、鮮度（90日以内確認率）

    更新漏れを検知する仕組み

    • ディスカバリ差分：ネットワーク上にあるがCMDBに無い／CMDBにあるが応答しない
    • 監視ツール差分：監視対象一覧とCMDBの稼働中CIを突合
    • チケット突合：完了した変更チケットの対象CIの updated_at が変更日より古い
    • 鮮度アラート：verified_at が一定期間を超えたCI
    • 契約突合：保守ベンダーの対象シリアル一覧とCMDBを年1〜2回突合

    8-5. 定期棚卸しの進め方

    頻度対象方法
    週次自動収集の差分差分キューを担当者が処理（登録・撤去・無視の判断）
    月次サンプリングランダム抽出したCIを実機・現地写真等で照合、品質KPIを報告
    四半期契約・期限保守期限・EOLの近いCI、契約未紐付けCIを確認
    年次全体棚卸し拠点ごとに現地/リモートで確認（700拠点は地域ごとに年間でローテーション）

    8-6. データ責任者（Owner）の設定

    • CIクラスごとにオーナーを設定する（例：回線＝NW企画G、AP＝無線担当チーム）。
    • オーナーは「自分で全部入力する人」ではなく「正しさに責任を持ち、品質KPIをレビューする人」。
    • オーナー不在のCIを定期的に抽出し、「オーナーが決まらないCIは管理対象から外す」ことも検討する。

    • CIが数千件を超え、ファイルが重い・壊れる
    • 複数人の同時更新で上書き事故が起きる
    • 「AのサービスはどのCIに依存するか」を多段でたどる要求が頻繁にある
    • 自動収集結果を定期的に取り込みたい
    • 変更・インシデントのチケットと自動で紐付けたい
    移行を楽にするためにExcelの段階から「CI ID」「関係を別シートで1行1件」「マスタ値の固定」を守っておくと、DBや製品へのインポートがほぼそのまま可能です。逆に、セル結合・色による意味付け・備考欄への自由記述は、移行時の最大の障害になります。

    失敗パターン失敗例原因対策
    項目を増やしすぎる機器1台に80項目。半分以上が空欄で、誰も入力しなくなった「あれば便利」で項目を追加。使い道と情報源を確認していない項目ごとに「使う業務」「情報源」「更新者」を定義。説明できない項目は入れない。充足率が低い項目は四半期ごとに見直す

    CIの粒度が不適切スイッチのポートまでCI化して更新が破綻／逆に「拠点NW一式」で交換対象が分からない交換・変更・障害の単位を考えずに決めた3章の「粒度を決める5つの問い」で判断。細かい情報は自動収集の参照データにする

    目的が曖昧「ITILに沿ってCMDBを作る」がゴールになり、何に使うか誰も説明できない手段と目的の取り違え解決する業務課題とKPI（例：影響調査時間を30分→5分）を最初に定義
    責任者が決まっていない不整合を見つけても「誰が直すのか」で止まるオーナー・更新担当の未定義CIクラスごとにオーナーを設定。RACIを明文化
    自動収集に依存しすぎるディスカバリで1万件取り込んだが、未知の機器や検証機が混在し、重複も多数「自動なら正しい」という思い込み。識別ルール不在自動収集は「候補」として取り込み、識別ルールと人の確認を経て登録。自動化できない属性（オーナー、サービス関係）を明確化
    データの正確性を確認しない監査で実機照合したら一致率70%。CMDBへの信頼が失われ使われなくなった品質の測定・報告の仕組みがない月次サンプリング、品質KPIの定期報告。不正確な情報には信頼度フラグを付ける
    導入自体が目的になる高額なツールを導入し、構築プロジェクトが完了した時点で活動が終わった運用設計・定着化の計画と予算がない導入後の運用体制・工数を先に確保。「導入完了」ではなく「業務KPIの改善」を成功基準にする
    共通する教訓CMDBの成否は、ツールの機能よりも「目的の明確さ」「更新が業務に組み込まれているか」「責任者がいるか」でほぼ決まります。

    13. 用語集・参考知識

    この章のゴール：重要用語を正確に理解し、ITILにおけるCMDBの位置付けを誤解なく説明できるようになる。

    用語説明
    CI（Configuration Item）構成アイテム。ITサービスを提供するために管理が必要な構成要素。機器、ソフトウェア、回線、サービス、文書など
    CI ClassCIの分類（ルータ、回線、サービスなど）。クラスごとに持つ属性が決まる。上位クラスから属性を継承する設計が多い
    Attribute（属性）CIの特徴を表すデータ項目（ホスト名、シリアル、ステータス等）
    Relationship（関係）CI同士のつながり。種類（依存・接続・設置など）と向きを持つ。影響分析の基盤
    Baseline（ベースライン）ある時点で合意・承認された構成の状態。変更前後の比較、復旧の基準、標準構成として使う（例：タイプB拠点標準構成 v3）
    Configuration Management（構成管理）構成情報を正確に保ち、必要なときに提供する活動。CMDBはその道具
    CMDBCIと関係の情報をライフサイクルを通じて記録するデータベース
    CMS（Configuration Management System）構成管理を支えるツール・データ・情報の集合。ITIL v3/2011では、1つ以上のCMDBを含みうる上位の仕組みとして説明されていた
    Discovery（ディスカバリ）ネットワークをスキャンし、機器・ソフトウェア・接続関係を自動検出すること。CMDBへの入力源
    Reconciliation（突合・調整）複数の情報源のデータを識別ルールで照合し、同一CIとしてまとめる処理
    ITSMITサービスマネジメント。ITを顧客価値のある「サービス」として設計・提供・改善する管理活動
    Service（サービス）顧客が望む成果の達成を支援し、価値を共創する手段。CMDBでは技術サービス・業務サービスとしてCI化する
    Incident（インシデント）サービスの計画外の中断、または品質の低下。例：横浜港北店のWAN断
    Problem（問題）1つ以上のインシデントの原因、または潜在的な原因。例：同型スイッチの電源故障多発
    Known Error（既知のエラー）原因が分析済みで、まだ解決されていない問題。回避策とともにナレッジに記録する
    Change（変更）サービスに直接・間接に影響しうるものの追加・変更・削除。例：OS更新、VLAN新設
    RFC変更要求（Request for Change）。変更を申請する記録
    CAB変更諮問委員会（Change Advisory Board）。変更の評価・承認に助言する場。ITIL 4では、より柔軟な変更承認の形が推奨されている
    Asset（資産）組織にとって価値のあるもの。IT資産は財務的価値を持ち、ITサービス提供に寄与する構成要素。資産管理は財務・契約の観点で管理する
    SPOF単一障害点（Single Point of Failure）。そこが壊れると全体が止まる箇所
    EOS / EOL販売終了／サポート終了など。定義と名称はメーカーにより異なるため、どの日付かを明確にして管理する
    IPAMIPアドレス管理（IP Address Management）。IPアドレス・サブネットの割当を管理する仕組み
    Single Source of Truthある情報について「正」とする唯一の情報源

    ※ Service、Incident、Problem、Change、Assetなどの説明はITILの定義を要約したものです。正確な定義文は公式出版物を確認してください。

    13-1. ITILにおけるCMDB・構成管理の位置付け

    版構成管理の扱い（概要）
    ITIL v3 / ITIL 2011サービストランジション（Service Transition）の中の「サービス資産管理および構成管理（SACM：Service Asset and Configuration Management）」プロセスとして説明されていた。CMS・CMDB・DML（決定版メディアライブラリ）などの概念が示されていた
    ITIL 4（2019〜）「プロセス」ではなく「プラクティス」という考え方を採用。構成管理は「サービス構成管理（Service Configuration Management）」、資産管理は「IT資産管理（IT Asset Management）」という別々のプラクティスとして整理されている。変更については、Foundation書籍（2019）では「Change Control」、その後のプラクティスガイドなどでは「Change Enablement」の名称が使われている
    正確に理解するための注意点
    • ITILはフレームワーク（ガイダンス）であり、「この項目を必ず管理せよ」と規定する規格ではありません。CMDBの項目・粒度・ツールは、組織の目的に合わせて決めるものです。
    • 認証可能な国際規格としては ISO/IEC 20000-1（ITサービスマネジメントシステム）があり、構成情報の管理に関する要求事項を含みます。IT資産管理については ISO/IEC 19770 シリーズがあります。具体的な要求事項の文言は規格本文で確認してください。
    • ITIL 4では、構成情報を単一の巨大なデータベースに集約することを必須とはしておらず、複数のツールやデータソースを組み合わせて必要な情報を提供するという考え方も示されています（解釈には幅があるため、原典の確認を推奨します）。
    • ITILの版・名称・定義は改訂されることがあります。本教材の記述は作成時点の一般的な理解に基づくもので、最新の公式情報（PeopleCert/AXELOS の公式出版物）で確認してください。ITIL®はPeopleCert（AXELOS）グループの登録商標です。
